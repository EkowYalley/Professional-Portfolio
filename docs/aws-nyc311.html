AWS NYC 311 Resolution Modeling

A corrected, leakage-safe baseline for classifying whether a public service request will close within 72 hours.

The question

Can information available when a 311 request is created help distinguish requests that close within 72 hours from those that take longer?

Why the framing matters: the target is calculated from creation and closure timestamps, but closure information is never used as a model feature.

Data and scope

The final workflow uses 49,999 valid, closed NYC 311 records. It checks timestamp order, removes unusable rows, derives the 72-hour target, and documents the final class distribution.

The sample supports a historical classification exercise. It does not represent open requests in production, and it does not prove the model will generalize across agencies or time periods.

What I built

  1. Python preparation and validation for timestamps, missing values, and categorical inputs.
  2. A preprocessing pipeline with one-hot encoding and a logistic-regression baseline.
  3. A train/test evaluation workflow with metrics beyond headline accuracy.
  4. A documented AWS path using S3 and Athena SQL, plus reproducible local instructions.

Results

Accuracy78.71%

Majority-class benchmark59.47%

Validation

Six automated checks cover the target definition, timestamp logic, train/test separation, row counts, feature leakage, and metric generation. The repository also records the target bug found in the earlier version: weekday was mistakenly used as the response variable.

Limitations and next step

  • Only closed requests are included, creating selection bias relative to live operational queues.
  • The model estimates association, not the effect of any intervention.
  • A production version would require time-based validation, calibration checks, agency-level error analysis, and monitoring for drift.
