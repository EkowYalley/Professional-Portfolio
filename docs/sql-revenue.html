Rental Revenue Analysis in SQL

A reproducible analysis of actor- and category-level revenue in the fictional Sakila rental database, with unmatched payments measured rather than hidden.

The question

How can a normalized rental database be turned into decision-ready revenue summaries while preserving the difference between total payments and payments that successfully connect through the analytical join path?

Data and reconciliation

Interpretation: the actor result is revenue associated with films in which an actor appears. It is not a causal measure of that actor’s contribution to demand.

What I built

  • MySQL queries using joins, grouped aggregation, common table expressions, and window functions.
  • A Dockerized database setup using the canonical Sakila fixture.
  • A Python and SQLAlchemy notebook path for running queries and reviewing outputs.
  • Saved result tables and a README that explains setup, assumptions, checks, and limitations.

Quality controls

Five checks verify core table counts, actor coverage, payment totals, linked revenue, and the unmatched-payment exception. Query-plan review and spot checks are documented alongside the main workflow.

Limitations and next step

  • Sakila is a fictional teaching database, so the commercial recommendations are illustrative.
  • Revenue association can double-count a film across multiple actors if treated as additive actor value.
  • A business version should add customer cohorts, rental frequency, inventory availability, and margin—not revenue alone.
